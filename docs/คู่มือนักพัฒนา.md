# ก.1 การประกอบและตั้งค่าอุปกรณ์

## ก.1.1 รายการอุปกรณ์หลัก

| อุปกรณ์ | คุณลักษณะที่ใช้จริง | หมายเหตุ |
|---|---|---|
| Raspberry Pi 5 | RAM 4 GB ขึ้นไป, Raspberry Pi OS 64-bit (Bookworm) | ระบบปฏิบัติการต้องเป็น 64-bit เพราะ `dlib` และ `python3-opencv` จาก apt เป็น 64-bit |
| microSD | 32 GB ขึ้นไป Class 10 | พื้นที่ว่างหลังติดตั้งควรเหลือ 8 GB ขึ้นไป |
| อะแดปเตอร์จ่ายไฟ | 5V **5A** (USB-C, PD) | Pi 5 ต้องการ 5A ถ้าใช้ 3A ของ Pi 4 จะจ่ายไฟให้พอร์ต USB ไม่พอ |
| กล้องเว็บแคม USB | OKER ความละเอียด 720p ขึ้นไป | ต่อผ่าน USB · โปรแกรมเปิดที่ **640 × 480** เป็นค่าเริ่มต้น (`pi_agent.py` บรรทัด 157–158) |
| จอแสดงผล | HDMI ขนาดใดก็ได้ | จำเป็นเฉพาะเมื่อต้องการแสดงกรอบและผลลัพธ์ให้นักศึกษาเห็น ดู ก.1.2 ขั้นที่ 7 |
| เครือข่าย | Wi-Fi หรือ LAN ที่ออกอินเทอร์เน็ตได้ | ต้องเข้าถึง `*.supabase.co` ผ่าน HTTPS ได้ ดู ก.1.4 |

> โปรแกรมรองรับกล้อง CSI (Raspberry Pi Camera Module ต่อผ่านสายริบบิ้น) ด้วย โดยลอง
> CSI ก่อนแล้วถอยไปใช้ USB (`camera.py` บรรทัด 53 และ 73) บังคับเลือกได้ด้วย
> `--source usb` หรือ `--source csi` **การทดสอบในโครงงานนี้ใช้เว็บแคม USB**

## ก.1.2 ขั้นตอนการเปิดเครื่องและตั้งค่าครั้งแรก

ทุกขั้นมีวิธีตรวจว่าทำสำเร็จแล้วต่อท้าย

**1. เขียนระบบปฏิบัติการลง microSD**

ใช้ Raspberry Pi Imager เลือก Raspberry Pi OS (64-bit) แล้วตั้งชื่อผู้ใช้เป็น `pi`

*ตรวจ:* `uname -m` ต้องได้ `aarch64` ถ้าได้ `armv7l` คือลง 32-bit มา ต้องเขียนใหม่

**2. ตั้งเวลาและเปิดบริการซิงก์เวลา**

ทำครบทั้งสามคำสั่ง ข้ามข้อใดข้อหนึ่งไม่ได้

```bash
sudo timedatectl set-timezone Asia/Bangkok
sudo timedatectl set-ntp true
sudo systemctl enable systemd-time-wait-sync
```

*ตรวจ:*

```bash
timedatectl
```

ต้องเห็นครบสามบรรทัดนี้

```
               Time zone: Asia/Bangkok (+07, +0700)
 System clock synchronized: yes
              NTP service: active
```

ถ้า `System clock synchronized` เป็น `no` แปลว่ายังซิงก์ไม่สำเร็จ
รอสักครู่แล้วสั่งซ้ำ ถ้ายังไม่ขึ้น `yes` มักเป็นเพราะเครือข่ายบล็อกพอร์ต NTP (UDP 123)
หรือยังติด captive portal — ดู ก.1.4

*ตรวจว่า unit รอซิงก์จริง:*

```bash
systemctl is-enabled systemd-time-wait-sync   # ต้องได้ enabled
systemctl show smartattend.service -p After | tr ' ' '\n' | grep time-sync
```

> **ทำไมต้องเปิด `systemd-time-wait-sync` ด้วย**
> Raspberry Pi ไม่มีนาฬิกาสำรอง (RTC) เมื่อบูตขึ้นมา เวลาของเครื่องจะย้อนไปเท่ากับ
> ตอนปิดเครื่องครั้งล่าสุด จนกว่าจะซิงก์จากอินเทอร์เน็ตสำเร็จ
> ไฟล์ unit ของ SmartAttend สั่ง `After=time-sync.target` ไว้แล้ว แต่ target นั้นจะ
> "ผ่านทันที" โดยไม่รออะไรเลยถ้าไม่มีบริการใดประกาศตัวว่าเป็นผู้ทำให้มันสำเร็จ
> `systemd-time-wait-sync` คือบริการนั้น เปิดแล้วโปรแกรมจะไม่เริ่มจนกว่านาฬิกาจะตรง
>
> เวลาที่บันทึกลงฐานข้อมูล **ไม่ได้รับผลกระทบอยู่แล้ว** เพราะ `record_attendance()`
> ใช้ `now()` ของเซิร์ฟเวอร์ตัดสินตรงเวลา/มาสาย ไม่ได้เชื่อเวลาที่อุปกรณ์ส่งมา (ดู ก.8)
> ที่ขั้นนี้แก้คือความถูกต้องของ **บันทึกการทำงาน** เพื่อให้ไล่ปัญหาย้อนหลังได้

**3. คัดลอกโปรแกรมและติดตั้ง**

```bash
cd ~
git clone <your-repo-url> smartattend
cd smartattend/smartattend_pi
chmod +x install.sh
./install.sh
```

*ตรวจ:* จบด้วยข้อความ `ติดตั้งเสร็จเรียบร้อย` และมีโฟลเดอร์ `.venv/` เกิดขึ้น

> `install.sh` ลอง `apt install python3-dlib` ก่อน ซึ่งใช้เวลาไม่กี่นาที ถ้า apt ไม่มีจะ
> คอมไพล์เอง ซึ่งใช้เวลานาน (บน Pi 4 เคยวัดได้ 20–40 นาที **ยังไม่ได้วัดบน Pi 5**
> คาดว่าเร็วกว่าแต่ยังเป็นหลักสิบนาที) ปล่อยทิ้งไว้ได้ อย่าปิดเครื่องกลางคัน

**4. ตั้งค่าการเชื่อมต่อฐานข้อมูล**

```bash
cp .env.example .env
nano .env
```

ใส่ค่าสามตัวตามคำอธิบายในไฟล์ (`SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, `DEVICE_CODE`)

*ตรวจ:*

```bash
source .venv/bin/activate
python -c "import supabase_client as sb; print('เชื่อมต่อได้', len(sb.get_open_session() or {}) >= 0)"
```

ไม่ขึ้น error คือตั้งค่าถูก ถ้าขึ้น `ไม่พบ SUPABASE_URL หรือ SUPABASE_SERVICE_KEY`
คือไฟล์ `.env` ยังไม่ถูกอ่าน

**5. ตรวจว่าระบบเห็นกล้อง**

```bash
source .venv/bin/activate
python camera.py
```

*ตรวจ:* สคริปต์จะไล่รายการกล้องที่พบพร้อมความละเอียด ถ้าไม่พบเลยให้ดู ก.1.5

**6. ทดลองรันจริง**

```bash
python pi_agent.py
```

*ตรวจ:* เห็นหน้าต่างกล้องและข้อความ `Waiting for class...` เมื่ออาจารย์ยังไม่เปิดคาบ

**7. ตั้งให้รันอัตโนมัติเมื่อเปิดเครื่อง**

ไฟล์ unit ชื่อ **`smartattend.service`** ตรงกับชื่อไฟล์จริงในโฟลเดอร์ `smartattend_pi/`
`install.sh` **ไม่ได้ติดตั้งให้** เพราะต้องใช้ sudo จึงต้องทำเองขั้นนี้

> ⚠️ **ชื่อไฟล์นี้เคยเขียนไม่ตรงกัน** ภาคผนวก ก ของเล่มปริญญานิพนธ์เขียนว่า
> `smartattend-display.service` ซึ่ง**ไม่มีอยู่จริง** ชื่อที่ถูกต้องคือ
> `smartattend.service` ตามไฟล์ในโค้ด ถ้าพิมพ์ตามเล่มจะได้ `Unit not found`
> รายการที่ต้องแก้ในเล่มอยู่ท้ายหัวข้อนี้

```bash
sudo cp smartattend.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable smartattend.service
sudo systemctl start smartattend.service
```

*ตรวจ:*

```bash
systemctl status smartattend.service          # ต้องเห็น active (running)
journalctl -u smartattend.service -f          # ดูบันทึกการทำงานสด
```

> unit ที่ให้มารันด้วย `--no-display` คือ **ไม่เปิดหน้าต่างกล้อง** เหมาะกับเครื่องที่ไม่มีจอ
> ถ้าต้องการให้นักศึกษาเห็นกรอบและผลลัพธ์บนจอ ต้องลบ `--no-display` ออกจากบรรทัด
> `ExecStart` ในไฟล์ unit **และ** ทำสองขั้นถัดไป

**8. เปิด Desktop Autologin (จำเป็นเฉพาะโหมดแสดงผลบนจอ)**

```bash
sudo raspi-config
# เลือก 1 System Options > S5 Boot / Auto Login > B4 Desktop Autologin
sudo reboot
```

*ตรวจ:* เปิดเครื่องแล้วเข้าหน้า Desktop เองโดยไม่ต้องพิมพ์รหัสผ่าน

**9. ปิด Screen Blanking (จำเป็นเฉพาะโหมดแสดงผลบนจอ)**

```bash
sudo raspi-config
# เลือก 2 Display Options > D4 Screen Blanking > No
sudo reboot
```

*ตรวจ:* ทิ้งเครื่องไว้ 15 นาทีโดยไม่แตะ จอต้องไม่ดับ

## ก.1.3 การติดตั้งตำแหน่งกล้อง

| เรื่อง | ค่าที่แนะนำ | เหตุผล |
|---|---|---|
| ระยะยืน | **50–60 ซม.** จากกล้อง | ใกล้กว่านี้ใบหน้าล้นเฟรม ไกลกว่านี้ใบหน้าเล็กเกินกว่าที่ตัวตรวจจับจะเจอ |
| ความสูงกล้อง | ระดับสายตา ประมาณ 150–165 ซม. จากพื้น | มุมกดหรือมุมเงยมากทำให้เวกเตอร์ใบหน้าต่างจากภาพลงทะเบียนที่ถ่ายตรงหน้า |
| ขนาดใบหน้าในภาพ | ไม่เล็กกว่า **80 พิกเซล** ด้านกว้าง | เล็กกว่านี้ตัวตรวจจับ HOG มักหาไม่เจอ ดูหมายเหตุเรื่องการย่อภาพด้านล่าง |
| ทิศทางแสง | ให้แสงมาจากด้านหน้าหรือด้านข้าง | แสงจากด้านหลังทำให้ใบหน้าเป็นเงาดำ ตรวจจับไม่ได้ |
| พื้นหลัง | เรียบ สีทึบ ไม่มีคนเดินผ่าน | ลดโอกาสที่ระบบจับใบหน้าของคนที่เดินผ่านด้านหลัง |
| หลีกเลี่ยง | ตั้งหน้าหน้าต่างหรือใต้หลอดไฟกะพริบ | ภาพสว่างจ้าหรือกะพริบทำให้ค่าความเชื่อมั่นแกว่ง ยืนยันไม่ครบ 3 เฟรม |

> **เรื่องการย่อภาพที่ต้องเข้าใจให้ตรงกัน** โปรแกรมเปิดกล้องที่ 640 × 480 แล้วย่อลง
> ด้วยตัวคูณ `downscale` ค่าเริ่มต้น **0.25** ก่อนตรวจจับใบหน้า (`pi_agent.py` บรรทัด 161
> ส่งค่าให้ `FaceRecognizer` ใน `face_recognizer.py` บรรทัด 115) เท่ากับตรวจจับที่
> **160 × 120** แล้วขยายพิกัดกลับ (`face_recognizer.py` บรรทัด 142 และ 160)
> ดังนั้นใบหน้า 80 พิกเซลในภาพต้นฉบับจะเหลือ 20 พิกเซลตอนตรวจจับ
> ถ้าพบว่าตรวจจับไม่เจอบ่อย ให้เพิ่มความละเอียดกล้องหรือเพิ่มค่า `downscale`
> เช่น `--width 1280 --height 720 --downscale 0.5` ซึ่งจะตรวจจับที่ 640 × 360

# ก.3 การติดตั้งและพัฒนาฝั่งเว็บ

```bash
cd smartattend_web
npm install
cp .env.example .env      # แล้วแก้ค่าให้ถูกต้อง
npm run dev
```

เปิด `http://localhost:5173` · ใน VS Code กด **F5** เลือก `▶ รันเว็บ + เปิดเบราว์เซอร์`
จะรันพร้อมเปิดเบราว์เซอร์ให้เอง แก้โค้ดแล้วกด Save หน้าเว็บอัปเดตทันที

### ตัวแปรสภาพแวดล้อมฝั่งเว็บ

| ตัวแปร | จำเป็น | หาค่าได้จาก | หมายเหตุ |
|---|---|---|---|
| `VITE_SUPABASE_URL` | ✅ | Dashboard > Project Settings > API > Project URL | ถ้าไม่มี แอปจะขึ้นข้อความว่าไม่พบค่าเชื่อมต่อฐานข้อมูล |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | ✅ | Dashboard > Project Settings > API > anon public | รองรับทั้งคีย์รูปแบบ JWT เดิมและรูปแบบใหม่ที่ขึ้นต้นด้วย `sb_publishable_` |
| `VITE_SUPABASE_PROJECT_ID` | — | Dashboard > Project Settings > General > Reference ID | ใช้เป็นข้อมูลอ้างอิงในหน้าผู้ดูแลระบบ |

ตัวแปรฝั่งเซิร์ฟเวอร์ตั้งใน Supabase ไม่ใช่ในไฟล์นี้ — `SUPABASE_SERVICE_ROLE_KEY`
(ทุก Edge Function ที่ทำงานแทนผู้ใช้) และ `GEMINI_API_KEY` (`parse-schedule-image` เท่านั้น)

> ตัวแปรที่ขึ้นต้นด้วย `VITE_` ถูกฝังลงไฟล์ JavaScript ที่ผู้ใช้ทุกคนดาวน์โหลด
> **ห้ามใส่ service_role key ที่นี่** การคุ้มครองข้อมูลมาจากนโยบาย RLS

### คำสั่งตรวจสอบก่อน commit

```bash
npx tsc -p tsconfig.app.json --noEmit   # ตรวจชนิดข้อมูล
npm run lint                            # ตรวจรูปแบบโค้ด
npm run test                            # รันชุดทดสอบ (vitest)
npm run build                           # สร้างไฟล์สำหรับ deploy
```

> ⚠️ ใช้ `npx tsc -p tsconfig.app.json --noEmit` ไม่ใช่ `npx tsc --noEmit` เพราะ
> `tsconfig.json` มี `"files": []` และมีแต่ project references ซึ่ง `tsc` จะข้ามถ้าไม่ระบุ
> โปรเจกต์ ทำให้คำสั่งสั้นผ่านทุกครั้งโดยไม่ได้ตรวจอะไรเลย (หรือใช้ `npx tsc -b`)

# ก.4 การทำ PWA และการ deploy

เว็บแอปนี้เป็น Progressive Web App ติดตั้งลงหน้าจอโฮมได้เหมือนแอปทั่วไป
โดยไม่ต้องผ่าน App Store หรือ Play Store

### deploy ขึ้น Vercel

```bash
cd smartattend_web
npm i -g vercel        # หรือใช้ npx vercel
vercel login
vercel --prod
```

> **ต้องตั้ง Environment Variables ใน Vercel ให้ครบก่อน deploy**
> Vercel > Project > Settings > Environment Variables ใส่ `VITE_SUPABASE_URL`,
> `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_SUPABASE_PROJECT_ID`
> ถ้าไม่ตั้ง หน้าเว็บจะขึ้นข้อความว่าไม่พบค่าเชื่อมต่อฐานข้อมูล
>
> ต้องรันจากในโฟลเดอร์ `smartattend_web` ไม่ใช่รากของ repo เพราะรากไม่มี `package.json`

### วิธีที่ผู้ใช้ติดตั้ง

# ก.5 การจัดการฐานข้อมูลและ Edge Functions

```bash
cd smartattend_web

# 1) ติดตั้ง Supabase CLI (ทำครั้งเดียวต่อเครื่อง)
npm i -g supabase          # หรือ brew install supabase/tap/supabase

# 2) ล็อกอิน จะเปิดเบราว์เซอร์ให้กดยืนยัน
supabase login

# 3) ผูกโฟลเดอร์นี้กับโปรเจกต์บนคลาวด์
#    หา project ref ได้ที่ Supabase Dashboard > Project Settings > General > Reference ID
supabase link --project-ref <your-project-ref>

# 4) ส่ง migration ทั้งหมดขึ้นฐานข้อมูล (ไล่ตามลำดับชื่อไฟล์)
supabase db push

# 5) deploy Edge Function
supabase functions deploy admin-create-user
supabase functions deploy start-class-session
# ...ทำทีละตัวตามชื่อโฟลเดอร์ใน supabase/functions/
```

`migration` ทุกไฟล์เขียนให้รันซ้ำได้ (idempotent) จึงสั่ง `db push` ซ้ำได้ไม่พัง
ลำดับการรันคือลำดับชื่อไฟล์ซึ่งขึ้นต้นด้วยวันเวลา ห้ามเปลี่ยนชื่อไฟล์ที่ push ไปแล้ว

# ก.6 ระบบคะแนน

## โครงสร้างสามระดับ

```
รายวิชา
└── หมวดคะแนน (grade_components)   ← ถือ "น้ำหนัก" เป็นเปอร์เซ็นต์ของวิชา
    └── รายการคะแนน (grade_items)  ← ถือ "คะแนนดิบเต็ม" ของงานชิ้นนั้น
        └── คะแนนรายคน (student_grades)
```

คะแนนเต็มของรายการเก็บเป็น **คะแนนดิบเสมอ** (ข้อสอบ 30 คะแนน เก็บเลข 30)
การแปลงเป็นเปอร์เซ็นต์ของวิชาเป็นหน้าที่ของโหมดคำนวณของหมวด
น้ำหนักของทุกหมวดต้องรวมเป็น 100 ก่อนประกาศผล แต่ระหว่างเทอมไม่ครบได้ กรอกคะแนนได้ปกติ

**กฎที่ใช้กับทุกโหมด** รายการที่ยังไม่ตรวจไม่ถูกนับเป็นศูนย์และไม่ถูกนับในตัวหาร ·
`null` (ยังไม่ตรวจ) ต่างจาก `0` (ตรวจแล้วได้ศูนย์) เด็ดขาด · ไม่ปัดเศษระหว่างคำนวณ

## โหมดที่หนึ่ง — ตามสัดส่วนคะแนนรวม (`proportional`)

คะแนนหมวด = (ผลรวมคะแนนที่ได้ ÷ ผลรวมคะแนนเต็มของหมวด) × น้ำหนักหมวด

**ตัวอย่างจริง** หมวด LABs น้ำหนัก 30% มีสามงาน เต็ม 10, 30, 60 คะแนน

| กรณี | คะแนนที่ได้ | คิดเป็น | ได้ / น้ำหนักที่ตรวจแล้ว |
|---|---|---|---|
| ตรวจครบ | 10, 15, 30 | (55 ÷ 100) × 30 | **16.50 / 30** = 55% |
| ตรวจครบ ได้เต็ม | 10, 30, 60 | (100 ÷ 100) × 30 | **30.00 / 30** = 100% |
| ตรวจแค่งานแรก | 10, –, – | (10 ÷ 100) × 30 | **3.00 / 3.00** = 100% ของที่ตรวจแล้ว |
| งานแรกได้ 0 | 0, 15, 30 | (45 ÷ 100) × 30 | **13.50 / 30** = 45% |
| งานแรกยังไม่ตรวจ | –, 15, 30 | (45 ÷ 100) × 30 | **13.50 / 27** = 50% |

สองแถวสุดท้ายแสดงว่าทำไม `null` ต้องต่างจาก `0` — ตัวตั้งเท่ากันแต่ตัวหารต่างกัน
คนที่ได้ศูนย์จริงได้ 45% คนที่ครูยังไม่ตรวจได้ 50% ของส่วนที่ตรวจแล้ว

## โหมดที่สอง — ถ่วงน้ำหนักรายการย่อย (`weighted_items`)

คะแนนหมวด = Σ (คะแนนที่ได้ ÷ คะแนนเต็มของรายการ × น้ำหนักย่อย) ÷ 100 × น้ำหนักหมวด

น้ำหนักย่อยของทุกรายการในหมวดต้องรวมเป็น 100 บังคับด้วย constraint trigger

**ตัวอย่างจริง** หมวดสอบกลางภาค 30% สามส่วน น้ำหนักย่อย 20 / 30 / 50 เต็ม 10 / 30 / 60

| กรณี | สัดส่วนที่ได้ | คิดเป็น | ได้ |
|---|---|---|---|
| ตรวจครบ | 1.0, 0.5, 0.5 | (1.0×20 + 0.5×30 + 0.5×50) ÷ 100 × 30 | **18.00 / 30** = 60% |
| ตรวจแค่ส่วนแรก | 1.0, –, – | (20 ÷ 100) × 30 | **6.00 / 6.00** = 100% |

บนข้อมูลชุดเดียวกัน โหมดแรกได้ 16.50 โหมดที่สองได้ 18.00 เพราะโหมดที่สองให้น้ำหนัก
ตามที่อาจารย์กำหนด ไม่ใช่ตามขนาดคะแนนเต็มของงาน

## การตัดคะแนนต่ำสุด (`drop_lowest`)

ตัดรายการที่ได้สัดส่วนคะแนนต่ำสุดออก นับเฉพาะรายการที่ **ตรวจแล้ว** ต้องเหลืออย่างน้อย
หนึ่งรายการ เสมอกันตัดตามลำดับที่อาจารย์จัดไว้ · **ตัวอย่าง** LABs เต็ม 10/30/60 ได้
10/15/15 → สัดส่วน 1.0 / 0.5 / 0.25 · ตั้ง `drop_lowest = 1` ตัดงานที่สาม เหลือ
(10+15) ÷ 40 × 30 = **18.75**

## คะแนนการเข้าเรียน

คะแนนหมวด = (Σ ค่าน้ำหนักตามสถานะ ÷ จำนวนคาบที่นับ) × น้ำหนักหมวด

| สถานะ | คอลัมน์ | ค่าเริ่มต้น |
|---|---|---|
| มาตรงเวลา | `credit_on_time` | 1.0 |
| มาสาย | `credit_late` | 0.5 |
| ลา | `credit_excused` | 1.0 |
| ขาดเรียน | `credit_absent` | 0.0 |

**คาบที่นับ** ต้องปิดแล้ว (`status = 'closed'`) ไม่ถูกยกเลิก และอยู่ในช่วงที่นักศึกษาคนนั้น
อยู่ในรายวิชา (ระหว่าง `joined_at` ถึง `withdrawn_at`) · คาบที่นับแต่ไม่มีระเบียนการเช็คชื่อ
ถือเป็นขาดเรียน

**ตัวอย่างจริง** หมวดเข้าเรียน 10% มาตรงเวลา 2 คาบ สาย 1 คาบ จาก 3 คาบที่นับ

| `credit_late` | การคำนวณ | ได้ |
|---|---|---|
| 0 | (2×1 + 1×0) ÷ 3 × 10 | 6.67 |
| 0.5 | (2×1 + 1×0.5) ÷ 3 × 10 | 8.33 |
| 1.0 | (2×1 + 1×1) ÷ 3 × 10 | 10.00 |

อาจารย์ที่ให้คนมาสายเต็มคะแนนตั้ง 1.0 อาจารย์ที่ไม่ให้เลยตั้ง 0 ระบบรองรับทั้งสองแบบ
โดยไม่ต้องแก้โค้ด · เกณฑ์ระงับสิทธิ์สอบเพราะขาดเรียนเป็นกลไกแยกจากเกณฑ์คะแนนนี้

## การปิดบังคะแนนปลายภาค

ทำที่ระดับฐานข้อมูลด้วยนโยบาย Row Level Security ไม่ใช่การซ่อนบนหน้าจอ นักศึกษายิง
คำสั่ง REST ตรงเข้าตารางก็ได้ผลลัพธ์ว่าง ไม่ใช่ได้ข้อมูลแล้วหน้าจอไม่แสดง

- แถวใน `student_grades` ที่เป็นคะแนนปลายภาคถูกกรองออกทั้งแถว
- การตัดสินว่าแถวใดเป็นคะแนนปลายภาคทำในฟังก์ชัน `SECURITY DEFINER` ไม่ใช่ในนิพจน์
  ของนโยบายโดยตรง เพราะ subquery ในนโยบายถูก RLS ของตารางที่มันอ้างถึงกรองด้วย
  ทำให้นโยบายตรวจไม่พบว่าแถวนั้นเป็นคะแนนปลายภาคแล้วปล่อยผ่าน ·
  `get_student_score_summary` เป็น `SECURITY INVOKER` โดยเจตนา เพื่อให้การปิดบัง
  มีจุดบังคับเดียวคือ RLS
- **ตัวอักษรเกรดไม่แสดงจนกว่าจะตรวจครบน้ำหนัก 100 และประกาศผลแล้ว** ก่อนหน้านั้น
  นักศึกษาเห็นแค่ว่าได้กี่คะแนนจากน้ำหนักที่ตรวจแล้ว

รายละเอียดสูตรฉบับเต็มอยู่ใน [docs/สูตรคำนวณคะแนน.md](สูตรคำนวณคะแนน.md)

# ก.8 ความปลอดภัย

**กุญแจ service role ใช้เฉพาะฝั่งอุปกรณ์** คีย์นี้ข้ามนโยบาย RLS ทั้งหมด อยู่ได้เฉพาะ
ในไฟล์ `.env` บนอุปกรณ์ที่ควบคุมทางกายภาพได้ ฝั่งเว็บใช้ publishable key ซึ่งออกแบบ
ให้เปิดเผยได้ และถูกคุ้มครองด้วย RLS

**สถานะ `verify_jwt` ของทุก Edge Function** เป็น `true` ทั้งหมด (`supabase/config.toml`)

| Edge Function | `verify_jwt` | ตรวจสิทธิ์เพิ่มในฟังก์ชัน |
|---|---|---|
| `admin-create-user` | `true` | ต้องมี role `admin` |
| `admin-delete-user` | `true` | ต้องมี role `admin` |
| `admin-review-role-request` | `true` | ต้องมี role `admin` |
| `import-course-roster` | `true` | ต้องมี role `instructor` หรือ `admin` และเขียนได้เฉพาะวิชาของตัวเอง |
| `manual-match-enrollment` | `true` | ตรวจความเป็นเจ้าของรายวิชาก่อนแก้ข้อมูล |
| `start-class-session` | `true` | ต้องเป็นผู้สอนของรายวิชานั้น |
| `parse-schedule-image` | `true` | ต้องมี role `instructor` หรือ `admin` · จำกัดภาพ 6 MB · จำกัด 20 ครั้ง/คน/ชั่วโมง |

> `verify_jwt` ยืนยันแค่ว่า "ล็อกอินอยู่" ไม่ได้บอกว่าเป็นใคร นักศึกษาทุกคนก็มี JWT
> ที่ใช้ได้ จึงต้องตรวจ role ในฟังก์ชันอีกชั้นทุกตัว

**การควบคุมสิทธิ์ระดับแถว (RLS)** เปิดใช้ทุกตารางที่มีข้อมูลผู้ใช้ นักศึกษาอ่านได้เฉพาะ
ของตัวเอง อาจารย์อ่านและแก้ได้เฉพาะรายวิชาของตัวเอง คะแนนปลายภาคถูกกรองออกทั้งแถว
ก่อนประกาศผล (ดู ก.6)

**การบันทึกประวัติ** ทุกการเปลี่ยนคะแนนถูกบันทึกใน `grade_audit_logs` พร้อมคนที่แก้
ค่าเดิม ค่าใหม่ เหตุผล และเวลา · การเปลี่ยนโครงสร้างคะแนน ประกาศผล ปลดล็อก และลบข้อมูล
ถูกบันทึกใน `audit_logs` · การแก้คะแนนที่บันทึกไว้แล้วต้องระบุเหตุผลก่อนบันทึก

**สิ่งที่เจ้าของระบบต้องทำเอง** อ่าน [SECURITY.md](../SECURITY.md) ซึ่งระบุช่องโหว่ที่แก้แล้ว
และสิ่งที่ต้องทำในหน้า Dashboard เช่นการเปลี่ยนรหัสผ่านและการหมุนคีย์

# ก.9 ข้อจำกัดที่ทราบ

**ยังไม่มีการตรวจว่าเป็นคนจริง (liveness detection)** ระบบยังแยกไม่ได้ระหว่างใบหน้าคนจริง
กับภาพถ่ายหรือภาพบนหน้าจอโทรศัพท์ที่ยกมาให้กล้องดู การกำหนดให้ต้องเจอคนเดิมติดกัน
3 เฟรมช่วยลดการทายผิดชั่ววูบ แต่ไม่ได้ป้องกันภาพนิ่ง **จึงยังไม่สามารถอ้างได้ว่าระบบ
ป้องกันการเช็คชื่อแทนได้สมบูรณ์** สิ่งที่ระบบทำได้จริงคือย้ายการเช็คชื่อมาไว้ที่อุปกรณ์
ประจำห้องเรียน ทำให้ต้องมีคนเดินมาที่กล้อง และทิ้งภาพหลักฐานไว้ทุกครั้ง

**แบบจำลอง CNN ฝั่งเว็บยังไม่ได้ถูกใช้ในการเช็คชื่อจริง** ดู ก.2.3

**อุปกรณ์ยังไม่มีคิวส่งซ้ำเมื่อเน็ตหลุด** ถ้าเครือข่ายหลุดระหว่างคาบ การเช็คชื่อช่วงนั้น
จะล้มเหลวและไม่ถูกส่งใหม่ นักศึกษาต้องสแกนซ้ำเมื่อเน็ตกลับมา

**`install.sh` ไม่ได้ติดตั้ง systemd service ให้** ต้องทำเองตาม ก.1.2 ขั้นที่ 7

**ภาพใบหน้าเก็บเป็น base64 ในคอลัมน์ฐานข้อมูล** ไม่ได้อยู่ใน Storage (คนละ 50 ภาพ)
ทำให้ตารางโตเร็วและดึงช้ากว่าที่ควร · มีสองตารางที่เก็บการลงทะเบียนรายวิชาซ้ำกัน คือ
`student_courses` และ `course_enrollments` (โค้ดใช้ตัวหลังเป็นหลัก) · `tsconfig` ยังปิด
`strict` อยู่ และยังมีการใช้ `any` หลายจุด · การส่งออก Excel ยังเป็นคอลัมน์รายการดิบ
ไม่มีคอลัมน์ยอดรวมของแต่ละหมวด
