## ก. รายการ RPC ทั้งหมด

คอลัมน์ "โหมด" — `DEFINER` คือรันด้วยสิทธิ์ของเจ้าของฟังก์ชัน จึง **ข้าม RLS**
และต้องตรวจสิทธิ์เองในตัวฟังก์ชัน · `INVOKER` คือรันด้วยสิทธิ์ของผู้เรียก RLS จึงยังทำงาน

คอลัมน์ "ใครเรียกได้" — `PUBLIC` หมายถึงทุกคนรวมผู้ที่ยังไม่ล็อกอิน

## ข. นโยบายสิทธิ์ที่บังคับอยู่จริงในแต่ละตาราง

ทุกตารางในสคีมา `public` **เปิด RLS ครบทั้ง 28 ตาราง** และมีอย่างน้อย 1 นโยบาย
ไม่มีตารางใดที่เปิด RLS แล้วลืมใส่นโยบาย (ซึ่งจะทำให้ไม่มีใครอ่านได้เลย)

> **เรื่องที่ต้องเข้าใจ** นโยบาย RLS หลายอันบนตารางเดียวกันจะ **OR กัน**
> ไม่ใช่ AND การเพิ่มนโยบายใหม่จึงเป็นการ "เปิดกว้างขึ้น" เสมอ ไม่ใช่เข้มขึ้น
> และ **สิทธิ์ระดับตาราง (GRANT) ถูกตรวจก่อน RLS** ถ้าไม่มี GRANT จะได้
> `permission denied` ตั้งแต่ก่อน RLS ได้ทำงาน

### หลักการที่ใช้ร่วมกันทุกตาราง

| บทบาท | เห็นอะไร |
|---|---|
| นักศึกษา | เฉพาะแถวที่ `student_id = auth.uid()` และต้องไม่ใช่คะแนนที่ถูกปิดบัง |
| อาจารย์ | เฉพาะรายวิชาที่ตัวเองเป็นผู้สอน ตรวจด้วย `is_course_instructor(course_id, auth.uid())` |
| ผู้ดูแลระบบ | ทุกแถว ตรวจด้วย `internal.has_role(auth.uid(), 'admin')` |
| ผู้ที่ยังไม่ล็อกอิน | ไม่เห็นอะไรเลย (ยืนยันแล้วในกรณี G-06a ถึง G-06c) |

### การปิดบังคะแนนปลายภาค

ทำสองชั้นซ้อนกัน ซึ่งยืนยันแล้วว่าได้ผลจริงในกรณี F-12

1. ตาราง `grade_items` — นักศึกษามองไม่เห็นแม้แต่ "หัวข้อ" ของคะแนนปลายภาค
   จนกว่า `courses.final_grade_published` จะเป็นจริง
2. ตาราง `student_grades` — แม้จะเดา `grade_item_id` ได้ก็ยังอ่านคะแนนไม่ได้

เหตุที่ต้องทำสองชั้นเพราะนโยบายที่อ้างตารางอื่นในเงื่อนไข `USING` จะถูก RLS ของ
ตารางนั้นกรองซ้ำอีกชั้น ปัญหานี้เคยเกิดและถูกแก้ใน migration `20260927210000`

## ค. ฟังก์ชันหรือหน้าจอที่ไม่มีใครเรียกใช้แล้ว

ตรวจด้วยการค้นชื่อฟังก์ชันทุกตัวในโฟลเดอร์ `smartattend_web/src`,
`smartattend_pi` และ `supabase/functions` รวมถึงในนโยบาย RLS และในฟังก์ชันอื่น

### ที่ดูเหมือนไม่ถูกใช้ แต่ตรวจแล้วยังใช้อยู่

| สิ่งที่ตรวจ | ใช้อยู่ที่ไหน |
|---|---|
| `claim_ai_quota` | Edge Function `parse-schedule-image/index.ts:136` |
| `grade_item_is_masked` | นโยบาย RLS ของ `student_grades` |
| `grade_item_hidden_from_students` | นโยบาย RLS ของ `grade_items` |
| `category_of_component_kind` | เรียกจากภายใน `save_component_items` |

ทั้งสี่ตัวนี้ไม่ปรากฏในโค้ดฝั่งหน้าจอ จึงดูเหมือนตายแล้วถ้าค้นแค่โฟลเดอร์ `src`
แต่ถูกเรียกจากชั้นอื่น **ไม่ควรลบ**

### ที่ไม่ถูกใช้จริง

| สิ่งที่พบ | รายละเอียด |
|---|---|
| `src/pages/Index.tsx` | ไม่มี route ใน `App.tsx` อ้างถึง ความคิดเห็นบรรทัดแรกในไฟล์เขียนว่า *"Update this page (the content is just a fallback if you fail to update the page)"* ซึ่งเป็นไฟล์ตั้งต้นที่เครื่องมือสร้างโครงการสร้างไว้ให้ ลบได้ |

**หมายเหตุ** ฟังก์ชัน `has_role` ใน schema `public` ถูกลบไปแล้วตั้งแต่ migration
`20260711075028` และย้ายไปอยู่ที่ `internal.has_role` แต่เคยมีฟังก์ชันที่ยังเรียก
ชื่อเดิมค้างอยู่จนทำให้ปุ่มบันทึกทุกปุ่มพังเมื่อเดือนกันยายน และแก้แล้วใน
`20260929100000` — migration นั้นมี DO block ที่สแกน `pg_proc` เพื่อกันไม่ให้
ปัญหาเดิมกลับมาอีก

## ง. ข้อสังเกตเพิ่มเติมที่พบระหว่างสำรวจ

1. **ชุด migration รันใหม่จากฐานข้อมูลว่างไม่ผ่าน 3 จุด** → DEF-007
2. **`get_scan_roster` เป็น `SECURITY DEFINER` แต่ไม่ตรวจสิทธิ์ และเปิดให้ PUBLIC** → DEF-001
3. ฟังก์ชัน `SECURITY DEFINER` อีกสองตัวที่เปิดให้ PUBLIC เรียกได้และควรตรวจต่อ
   คือ `grade_item_score_count` และ `course_grades_locked`
4. ตาราง `grade_audit_logs` มีนโยบาย RLS ให้อาจารย์อ่านได้ แต่ **ไม่มี `GRANT`
   เขียนไว้ใน migration** จึงพึ่ง default privileges ของ Supabase ทั้งหมด
   → ต้องยืนยันด้วยข้อ M-00 ในรายการตรวจสอบด้วยมือ
