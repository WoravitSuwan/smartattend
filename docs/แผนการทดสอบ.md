## 1. ขอบเขตและวิธีทดสอบ

### 1.1 สิ่งที่ทดสอบอัตโนมัติได้

ชุดทดสอบ `supabase/tests/qa/` สร้างฐานข้อมูล PostgreSQL ขึ้นมาใหม่ แล้ว
**apply ไฟล์ migration ทั้ง 60 ไฟล์ตามลำดับจริง** จึงได้สคีมาเต็มเหมือนที่ใช้งาน
ครบทั้ง 28 ตาราง 61 ฟังก์ชัน และ 64 นโยบาย RLS จากนั้นสร้างข้อมูลทดสอบที่ขึ้นต้น
ด้วย `TEST_` แล้วรันกรณีทดสอบในฐานะผู้ใช้จริง

```bash
./supabase/tests/qa/run-qa.sh                 # สร้างฐานข้อมูลใหม่ รันทั้งหมด แล้วลบทิ้ง
./supabase/tests/qa/run-qa.sh --keep          # เก็บข้อมูลทดสอบไว้ดูต่อ
./supabase/tests/qa/run-qa.sh --seed-only     # สร้างข้อมูลทดสอบอย่างเดียว
./supabase/tests/qa/run-qa.sh --teardown-only # ลบข้อมูลทดสอบอย่างเดียว

# ชี้ไปฐานข้อมูลอื่น (เช่น supabase start หรือฐานข้อมูลที่ deploy แล้ว)
DATABASE_URL=postgresql://... ./supabase/tests/qa/run-qa.sh
```

**เรื่องที่ต้องเข้าใจก่อนอ่านผล** — ทุกกรณีรันในฐานะ role `authenticated` หรือ `anon`
พร้อม `auth.uid()` จริงที่อ่านจาก `request.jwt.claims` เหมือนตอนเรียกผ่าน API
ไม่ได้รันในฐานะ `postgres` ซึ่งเป็น superuser ที่ข้าม RLS ทุกนโยบาย
ถ้ารันผิด role กรณีทดสอบด้านสิทธิ์จะผ่านหมดโดยไม่ได้ทดสอบอะไรเลย

### 1.2 ข้อจำกัดที่ต้องระบุให้ชัด

| เรื่อง | สถานะ |
|---|---|
| ฐานข้อมูลที่ใช้ทดสอบ | PostgreSQL 16 ในเครื่อง สร้างจาก migration ชุดเดียวกับที่ deploy **ไม่ใช่อินสแตนซ์ที่ deploy แล้ว** เพราะผู้ทดสอบอัตโนมัติไม่มีคีย์เข้าถึง |
| Edge Function 7 ตัว | เป็นบริการ Deno แยกต่างหาก เรียกจาก SQL ไม่ได้ → ทดสอบด้วยมือ |
| กล้อง / อุปกรณ์ Raspberry Pi | ต้องใช้ฮาร์ดแวร์จริง → ทดสอบด้วยมือ |
| หน้าจอและการนำทาง | ต้องมองเห็น → ทดสอบด้วยมือ |

เพื่อให้ชุดทดสอบรันบน PostgreSQL เปล่าได้ ต้องจำลองสิ่งที่ Supabase มีให้อยู่แล้ว
(`auth.users`, `auth.uid()`, role `anon`/`authenticated`/`service_role`,
publication `supabase_realtime` และสิทธิ์ระดับตารางที่ Supabase ตั้งให้ผ่าน
default privileges) ไว้ใน `sql/00_shim.sql`
**ข้อสมมติเรื่องสิทธิ์ระดับตารางต้องยืนยันกับฐานข้อมูลจริงด้วยคำสั่งในข้อ M-00
ของรายการตรวจสอบด้วยมือ**
