## DEF-001 — `get_scan_roster` คืนรายชื่อนักศึกษาทั้งห้องให้ใครก็ได้ (วิกฤต)

**อาการ** ฟังก์ชัน `public.get_scan_roster(_course_id uuid)` คืน `student_id`,
`student_code` และ `student_name` ของนักศึกษาทุกคนในรายวิชา โดย **ไม่ตรวจสิทธิ์ของ
ผู้เรียกเลย** และเปิดให้ `PUBLIC` เรียกได้ จึงเรียกได้แม้ยังไม่ล็อกอิน

**หลักฐานจากการทดสอบ**

| กรณี | ผู้เรียก | ผลที่ได้ |
|---|---|---|
| G-02h | นักศึกษาในรายวิชา (ไม่ใช่อาจารย์) | ได้รายชื่อครบ 4 คน |
| G-03e | อาจารย์ของ **รายวิชาอื่น** | ได้รายชื่อครบ 4 คน |
| G-06d | **ผู้ที่ยังไม่ล็อกอิน (role `anon`)** | ได้รายชื่อครบ 4 คน พร้อมรหัสและชื่อ-สกุล |

**สาเหตุ** `supabase/migrations/20260926090000_grade_components_and_scheduled_sessions.sql`

```sql
CREATE OR REPLACE FUNCTION public.get_scan_roster(_course_id uuid)
RETURNS TABLE (student_id uuid, student_code text, student_name text)
LANGUAGE sql STABLE SECURITY DEFINER          -- ← ข้าม RLS
...                                            -- ← ไม่มีการตรวจสิทธิ์ผู้เรียกในตัวฟังก์ชัน
GRANT EXECUTE ON FUNCTION public.get_scan_roster(uuid) TO authenticated, service_role;
```

ปัญหามีสองชั้นซ้อนกัน

1. ฟังก์ชันเป็น `SECURITY DEFINER` จึงข้าม RLS แต่ **ไม่มีเงื่อนไขตรวจว่าผู้เรียกเป็น
   อาจารย์ของรายวิชานั้นหรืออุปกรณ์** ต่างจาก RPC อื่นในระบบนี้ที่ตรวจทุกตัว
   เช่น `recalc_attendance_scores` มี `IF NOT (is_course_instructor(...) OR has_role(...))`
2. PostgreSQL ให้สิทธิ์ `EXECUTE` แก่ `PUBLIC` กับฟังก์ชันใหม่ทุกตัวโดยปริยาย
   migration นี้เขียน `GRANT` เพิ่มแต่ **ไม่ได้ `REVOKE ... FROM PUBLIC`**
   ตรวจสิทธิ์จริงในแคตตาล็อกได้ค่า `=X/postgres` ซึ่งแปลว่า PUBLIC เรียกได้

ความรุนแรงอยู่ที่ว่า `anon` key ถูกฝังอยู่ในไฟล์ JavaScript ที่ผู้ใช้ทุกคนดาวน์โหลด
ตามการออกแบบของ Supabase ใครก็ตามที่เปิดเว็บจึงมีคีย์นี้ เหลือเพียงต้องรู้ UUID
ของรายวิชาก็ดึงรายชื่อนักศึกษาทั้งห้องได้ ซึ่งเป็นข้อมูลส่วนบุคคล

**ข้อเสนอการแก้** เพิ่มการตรวจสิทธิ์ในตัวฟังก์ชัน และตัดสิทธิ์ของ PUBLIC

```sql
CREATE OR REPLACE FUNCTION public.get_scan_roster(_course_id uuid)
RETURNS TABLE (student_id uuid, student_code text, student_name text)
LANGUAGE plpgsql STABLE SECURITY DEFINER
SET search_path = public
AS $$
BEGIN
  -- อุปกรณ์ถือ service key จึงผ่านได้ ส่วนคนต้องเป็นอาจารย์ของรายวิชานั้นหรือแอดมิน
  IF COALESCE((current_setting('request.jwt.claims', true))::jsonb ->> 'role', '')
       <> 'service_role'
     AND NOT public.is_course_instructor(_course_id, auth.uid())
     AND NOT internal.has_role(auth.uid(), 'admin'::app_role) THEN
    RAISE EXCEPTION 'ไม่มีสิทธิ์ดูรายชื่อของรายวิชานี้'
      USING ERRCODE = 'insufficient_privilege';
  END IF;

  RETURN QUERY
  SELECT ce.student_id, p.student_code, p.name
  FROM public.course_enrollments ce
  LEFT JOIN public.profiles p ON p.user_id = ce.student_id
  WHERE ce.course_id = _course_id
    AND ce.status = 'confirmed'
    AND ce.student_id IS NOT NULL
    AND NOT ce.attendance_blocked;
END $$;

REVOKE ALL ON FUNCTION public.get_scan_roster(uuid) FROM PUBLIC, anon;
GRANT EXECUTE ON FUNCTION public.get_scan_roster(uuid) TO authenticated, service_role;
```

**ต้องตรวจเพิ่ม** ฟังก์ชัน `SECURITY DEFINER` ตัวอื่นที่เปิดให้ PUBLIC เรียกได้
และอาจมีปัญหาเดียวกัน พบจากแคตตาล็อกดังนี้ ควรไล่ตรวจทีละตัว

- `grade_item_score_count(uuid)` — คืนจำนวนคะแนนที่กรอกแล้วของหัวข้อใด ๆ
- `course_grades_locked(uuid)` — คืนสถานะล็อกของรายวิชาใด ๆ
- `cleanup_orphan_assignment_items`, `sync_scheduled_sessions`, `recompute_attendance_block`
  (เป็น trigger function จึงความเสี่ยงต่ำกว่า แต่ `sync_scheduled_sessions` เรียกตรงได้)

## DEF-002 — เขียนตรงเข้าตารางข้ามเพดานคะแนนเต็มได้ (สูง)

**อาการ** กฎ "คะแนนต้องไม่เกินคะแนนเต็มของหัวข้อ" ถูกบังคับไว้ใน RPC เท่านั้น
การ `UPDATE public.student_grades SET score = 9999` ตรง ๆ **ผ่านฉลุย**

**หลักฐาน** กรณี F-05

| ทาง | ผล |
|---|---|
| F-05a `upsert_student_grade(..., 9999, ...)` | ถูกปฏิเสธ — "คะแนนเกินคะแนนเต็ม — หัวข้อ TEST_LAB1 เต็ม 10 แต่ได้รับ 9999" |
| F-05b `save_student_grades([... score 9999])` | ถูกปฏิเสธ — `{"ok": false, "saved": 0, "errors": [{"reason": "เกินคะแนนเต็ม (10)"}]}` |
| **F-05c `UPDATE student_grades SET score = 9999`** | **สำเร็จ ไม่มีการปฏิเสธ** |

**สาเหตุ** `20260927140000_enforce_score_bounds.sql` อธิบายไว้เองว่าทำสองชั้น
แต่ชั้นที่เป็น CHECK constraint กันได้แค่ค่าติดลบ

```sql
ALTER TABLE public.student_grades
  ADD CONSTRAINT student_grades_score_nonnegative
  CHECK (score IS NULL OR (score >= 0 AND score <> 'NaN'::numeric));
```

ความเห็นในไฟล์ระบุเหตุผลไว้ว่า *"เพดานอ้างอิง `grade_items.max_score` ของอีกตาราง
จึงทำเป็น CHECK ไม่ได้"* ซึ่งถูกต้อง — แต่ทำเป็น **trigger** ได้

ที่ทำให้ช่องนี้ใช้ได้จริงคือ นโยบาย RLS ของ `student_grades` เปิดให้อาจารย์
เขียนตารางตรง ๆ ได้ทุกคำสั่ง

```sql
CREATE POLICY "Instructors manage grades of own courses" ON public.student_grades
  FOR ALL ...     -- ← ครอบคลุม INSERT/UPDATE/DELETE
```

อาจารย์ทุกคนถือ JWT ที่ยิง PostgREST ได้โดยตรง
(`PATCH /rest/v1/student_grades?id=eq.<id>`) จึงข้าม RPC ได้ทั้งหมด

**ข้อเสนอการแก้** ดูข้อเสนอรวมท้ายเอกสาร

## DEF-003 — เขียนตรงเข้าตารางข้ามการล็อกหลังประกาศผลได้ (สูง)

**อาการ** หลังประกาศผล คะแนนต้องถูกล็อกจนกว่าจะปลดล็อกพร้อมเหตุผล
RPC บังคับได้ถูกต้อง แต่การเขียนตรงเข้าตารางผ่านได้

**หลักฐาน** กรณี F-15 (รัน ณ ขณะ `course_grades_locked = true`)

| ทาง | ผล |
|---|---|
| F-15b `save_student_grades` | ถูกปฏิเสธ — "รายวิชานี้ประกาศผลแล้วและคะแนนถูกล็อก ต้องปลดล็อกพร้อมระบุเหตุผลก่อนแก้" |
| F-15c `upsert_student_grade` | ถูกปฏิเสธ — ข้อความเดียวกัน |
| **F-15d `UPDATE student_grades SET score = 3`** | **สำเร็จ ไม่มีการปฏิเสธ** |

ผลคือ การล็อกคะแนนหลังประกาศผล ซึ่งเป็นกลไกควบคุมความถูกต้องของผลการเรียน
ไม่มีผลบังคับจริงต่อผู้ที่เรียก API ตรง

## DEF-004 — แก้สถานะการเข้าเรียนย้อนหลังได้โดยไม่ต้องระบุเหตุผล (สูง)

**อาการ** ข้อกำหนดระบุว่าการแก้สถานะย้อนหลังต้องระบุเหตุผล แต่กฎนี้อยู่ใน
**หน้าจอเท่านั้น** ฐานข้อมูลไม่ได้บังคับ

**หลักฐาน** กรณี D-11 — `UPDATE public.attendance_records SET status = 'on_time',
edited_by = ..., edited_at = now()` โดยไม่ใส่ `edit_reason` **สำเร็จ**

**สาเหตุ** คอลัมน์ `edit_reason` ถูกเพิ่มไว้ที่
`20260806094800_...sql:4` แต่ไม่มี constraint หรือ trigger ใดบังคับ
ที่บังคับจริงคือหน้าจอ `src/pages/instructor/ManualAttendanceEditPage.tsx:81`

```ts
.update({ status: next, edited_by: user?.id, edited_at: now, edit_reason: reason.trim() })
```

ผลคือการแก้สถานะย้อนหลังที่ไม่มีเหตุผลกำกับจะไม่มีร่องรอยให้ตรวจสอบย้อนหลังได้
ซึ่งเป็นปัญหาโดยตรงถ้ามีการโต้แย้งเรื่องสิทธิ์สอบจากการขาดเรียน

## DEF-005 — เกรดบนหน้าจอนักศึกษาไม่ตรงกับเกรดที่ประกาศเป็นทางการ (สูง)

**อาการ** `get_student_score_summary` **คำนวณเกรดใหม่ทุกครั้ง** จากคะแนนปัจจุบัน
แทนที่จะอ่านเกรดที่ประกาศไว้ในตาราง `course_final_grades`
เมื่อมีการแก้คะแนนหลังประกาศผล นักศึกษาจะเห็นเกรดที่ **ไม่ตรงกับที่ส่งทะเบียน**
โดยไม่มีคำเตือนใด ๆ

**หลักฐาน** กรณี F-16d — ลำดับเหตุการณ์ที่ทดสอบจริง

1. ประกาศผล STU1 คะแนนรวม 92.10 → บันทึกเกรด **A** ใน `course_final_grades`
2. อาจารย์ปลดล็อกพร้อมเหตุผล แล้วแก้คะแนน LAB และตัดคะแนนกลางภาคจาก 88 เหลือ 0
3. **ยังไม่ได้สั่งประกาศผลใหม่** — `course_final_grades` จึงยังเป็น A
4. ผลที่ได้: **หน้าจอนักศึกษาแสดง C+ ขณะที่เกรดที่ประกาศไว้คือ A**

**สาเหตุ** `20260929120000_component_planned_item_count.sql`

```sql
'grade', CASE
           WHEN v_used <= 0 THEN NULL
           WHEN v_is_staff THEN public.grade_letter(_course_id, v_earned / v_used * 100)
           WHEN v_used >= 99.99 AND COALESCE(v_published, false) THEN
             public.grade_letter(_course_id, v_earned / v_used * 100)   -- ← คำนวณใหม่
           ELSE NULL
         END,
```

ไม่มีจุดใดอ่านจาก `course_final_grades` เลย ทั้งที่ตารางนั้นคือทะเบียนเกรดที่เป็นทางการ
และเป็นที่เดียวที่เก็บเกรดพิเศษอย่าง I หรือ W ที่อาจารย์กำหนดเอง

**ผลข้างเคียงอีกข้อ** ถ้าอาจารย์ให้เกรดพิเศษ (I / W) ตอนประกาศผล นักศึกษาจะไม่เห็น
เกรดนั้น แต่จะเห็นเกรดที่คำนวณจากคะแนนแทน

**ข้อเสนอการแก้** เมื่อรายวิชาประกาศผลแล้ว ให้อ่านเกรดจาก `course_final_grades`
เป็นหลัก และใช้ค่าที่คำนวณได้เฉพาะตอนที่ยังไม่ประกาศผลหรือสำหรับอาจารย์เท่านั้น

```sql
-- ภายในฟังก์ชัน เพิ่มการอ่านเกรดที่ประกาศไว้
SELECT grade INTO v_final_grade
  FROM public.course_final_grades
 WHERE course_id = _course_id AND student_id = v_student_id;

-- แล้วเปลี่ยนเงื่อนไขเป็น
'grade', CASE
           WHEN COALESCE(v_published, false) AND v_final_grade IS NOT NULL
             THEN v_final_grade                                   -- เกรดที่ประกาศจริง
           WHEN v_used <= 0 THEN NULL
           WHEN v_is_staff THEN public.grade_letter(_course_id, v_earned / v_used * 100)
           ELSE NULL
         END,
```

## DEF-006 — แก้คะแนนที่บันทึกแล้วได้โดยไม่ต้องระบุเหตุผล (ปานกลาง)

**อาการ** ข้อกำหนดระบุว่าการแก้คะแนนที่บันทึกแล้วต้องระบุเหตุผล
แต่ RPC ทั้งสองตัวรับค่า `_reason` เป็น `NULL` ได้

**หลักฐาน**

| กรณี | คำสั่ง | ผล |
|---|---|---|
| F-07a | `upsert_student_grade(item, student, 7, NULL, NULL)` | สำเร็จ |
| F-07b | `save_student_grades(course, [...], NULL)` | สำเร็จ |

**สาเหตุ** ทั้งสองฟังก์ชันเขียนแถวลง `grade_audit_logs` เสมอ (ซึ่งถูกต้อง)
แต่ไม่ได้ตรวจว่า `_reason` มีค่า จึงได้แถวประวัติที่ `reason` เป็น NULL
ซึ่งตรวจสอบย้อนหลังไม่ได้ว่าแก้เพราะอะไร

ข้อนี้ต่างจาก DEF-004 ตรงที่ประวัติยังถูกบันทึก (รู้ว่าใครแก้ จากเท่าไรเป็นเท่าไร)
ขาดแค่เหตุผล จึงจัดเป็นปานกลางไม่ใช่สูง

**ข้อเสนอการแก้** เพิ่มการตรวจเฉพาะกรณี "แก้ค่าที่มีอยู่แล้ว" (ไม่ใช่กรอกครั้งแรก)

```sql
IF _old_score IS NOT NULL AND _old_score IS DISTINCT FROM _score
   AND COALESCE(btrim(_reason), '') = '' THEN
  RAISE EXCEPTION 'การแก้คะแนนที่บันทึกไว้แล้วต้องระบุเหตุผล'
    USING ERRCODE = 'check_violation';
END IF;
```

**ต้องตัดสินใจก่อนแก้** ถ้าบังคับเหตุผลกับการกรอกครั้งแรกด้วย อาจารย์จะต้องพิมพ์
เหตุผลทุกช่องตอนกรอกคะแนนครั้งแรกทั้งห้อง ซึ่งน่าจะใช้งานจริงไม่ได้
ข้อเสนอข้างบนจึงบังคับเฉพาะตอนแก้ค่าที่มีอยู่แล้ว **แต่ข้อนี้เป็นการตัดสินใจเชิงนโยบาย
ที่ควรยืนยันก่อนลงมือ**

## DEF-007 — ชุด migration รันใหม่จากฐานข้อมูลว่างไม่ผ่าน (ปานกลาง)

**อาการ** การ apply ไฟล์ migration ทั้ง 60 ไฟล์ตามลำดับลงฐานข้อมูลว่าง **ล้มเหลว
3 จุด** ระบบที่ใช้งานอยู่ไม่กระทบ แต่หมายความว่า **สร้างสภาพแวดล้อมใหม่จาก
ที่เก็บซอร์สโค้ดไม่ได้** ไม่ว่าจะเพื่อกู้คืน ทำระบบทดสอบ หรือส่งมอบ

**จุดที่ล้มเหลว**

| ไฟล์ | ข้อความผิดพลาด | สาเหตุ |
|---|---|---|
| `20260927100000_fix_attendance_rate.sql` | `cannot change data type of view column "on_time_count" from bigint to integer` | เพิ่ม `::int` ให้คอลัมน์ของวิว |
| `20260927230000_attendance_score_and_cancelled_sessions.sql` | `cannot change return type of existing function` | `recalc_attendance_scores` เปลี่ยน `RETURNS void` → `RETURNS jsonb` |
| `20260929021502_fix_attendance_summary_view.sql` | `cannot change data type of view column "on_time_count" from integer to bigint` | ถอด `::int` ออก ทำให้ชนิดกลับเป็น bigint |

วิว `v_attendance_summary` ถูกนิยามใหม่สามครั้งโดยชนิดคอลัมน์สลับไปมา
bigint → integer → bigint ซึ่ง `CREATE OR REPLACE VIEW` ไม่อนุญาต
ส่วน `CREATE OR REPLACE FUNCTION` ก็เปลี่ยนชนิดที่คืนไม่ได้เช่นกัน

**ข้อกังวลที่ตามมาและต้องตรวจกับฐานข้อมูลจริง** ถ้า migration สองไฟล์นี้เคยล้มเหลว
ตอน push จริง ฐานข้อมูลที่ใช้งานอยู่อาจยังมี `recalc_attendance_scores` ที่
`RETURNS void` อยู่ ซึ่งจะทำให้หน้าคำนวณคะแนนเข้าเรียนพัง เพราะหน้าจออ่านค่า
`.updated` และ `.skipped` จากผลลัพธ์ที่คาดว่าเป็น jsonb
(`src/lib/attendance-score-data.ts:73`) → **ดูข้อ M-01 ในรายการตรวจสอบด้วยมือ**

**ข้อเสนอการแก้** เพิ่ม migration ใหม่ (ไม่แก้ไฟล์เดิม เพราะไฟล์เดิมถูก apply ไปแล้ว)
ที่ `DROP` ก่อน `CREATE` ให้ชัดเจน

```sql
-- migration ใหม่: 20261013100000_fix_replayable_migrations.sql
DROP VIEW IF EXISTS public.v_attendance_summary CASCADE;
CREATE VIEW public.v_attendance_summary ... ;   -- นิยามล่าสุดจาก 20260929021502

DROP FUNCTION IF EXISTS public.recalc_attendance_scores(uuid) CASCADE;
CREATE FUNCTION public.recalc_attendance_scores(_course_id uuid) RETURNS jsonb ... ;
```

ชุดทดสอบ `run-qa.sh` มีการ `DROP` ชดเชยไว้ชั่วคราวพร้อมคำอธิบายกำกับ
**เมื่อแก้ข้อนี้แล้วให้ลบส่วนชดเชยนั้นออก** ไม่งั้นจะปิดบังปัญหาเดิมถ้ากลับมาอีก

## DEF-008 — ประวัติ commit ยังมี URL โปรเจกต์และ publishable key (ต่ำ)

**อาการ** ไฟล์ที่ track อยู่ปัจจุบันสะอาด แต่ commit สองรายการในประวัติยังมี
ไฟล์ `.env` ที่มีค่าจริง

| commit | หัวข้อ | สิ่งที่หลุด |
|---|---|---|
| `784eda8` | "Commit smartattend_web/.env with the project's Supabase URL and publishable key" | URL โปรเจกต์ + publishable key |
| `d4509d1` | "database" | ค่าเดียวกัน |

**ประเมินความรุนแรง** จัดเป็น **ต่ำ** เพราะ

- publishable key (เดิมเรียก anon key) **ออกแบบมาให้เปิดเผยได้** และถูกฝังอยู่ใน
  ไฟล์ JavaScript ที่ผู้ใช้ทุกคนดาวน์โหลดอยู่แล้ว การคุ้มครองข้อมูลมาจาก RLS
- **ไม่พบ `service_role` key** ในประวัติ ซึ่งเป็นคีย์ที่หลุดแล้วอันตรายจริง

แต่ยังควรจัดการ เพราะ URL โปรเจกต์ที่เปิดเผยทำให้ผู้ไม่หวังดีรู้ปลายทางที่จะยิง
ซึ่งเมื่อรวมกับ **DEF-001** จะกลายเป็นการเข้าถึงรายชื่อนักศึกษาได้จริงทันที

**ข้อเสนอ** ตามลำดับความสำคัญ

1. **แก้ DEF-001 ก่อน** เพราะเป็นตัวที่ทำให้ URL ที่หลุดมีค่าสำหรับผู้โจมตี
2. หมุน publishable key ใน Supabase Dashboard แล้วตั้งค่าใหม่ใน Vercel
3. การล้างประวัติ commit (เช่น `git filter-repo`) **ผู้ทดสอบไม่ได้ทำและไม่เสนอให้ทำ
   ตอนนี้** เพราะเขียนประวัติใหม่จะทำให้สำเนาที่คนอื่นโคลนไว้ใช้ต่อไม่ได้
   และข้อมูลที่หลุดไม่ใช่ความลับจริง — เป็นการตัดสินใจของเจ้าของโครงการ

## ข้อเสนอรวมสำหรับ DEF-002, DEF-003, DEF-004

ทั้งสามข้อมีสาเหตุเดียวกัน แก้ด้วยวิธีเดียวกันได้ คือย้ายกฎจาก RPC ลงไปที่
**trigger ระดับตาราง** ซึ่งบังคับกับทุกเส้นทางที่เขียนข้อมูล ไม่ว่าจะมาทาง RPC
ทาง PostgREST หรือทาง SQL ตรง

```sql
-- กันคะแนนเกินเต็มและกันการแก้หลังล็อก (DEF-002 + DEF-003)
CREATE OR REPLACE FUNCTION public.enforce_student_grade_rules()
RETURNS trigger LANGUAGE plpgsql SET search_path = public AS $$
DECLARE v_max numeric; v_course uuid; v_name text;
BEGIN
  SELECT gi.max_score, gi.course_id, gi.name INTO v_max, v_course, v_name
  FROM public.grade_items gi WHERE gi.id = NEW.grade_item_id;

  IF NEW.score IS NOT NULL AND v_max IS NOT NULL AND NEW.score > v_max THEN
    RAISE EXCEPTION 'คะแนนเกินคะแนนเต็ม — หัวข้อ "%" เต็ม % แต่ได้รับ %',
      v_name, v_max, NEW.score USING ERRCODE = 'check_violation';
  END IF;

  IF public.course_grades_locked(v_course) THEN
    RAISE EXCEPTION 'รายวิชานี้ประกาศผลแล้วและคะแนนถูกล็อก ต้องปลดล็อกก่อนแก้'
      USING ERRCODE = 'check_violation';
  END IF;

  RETURN NEW;
END $$;

CREATE TRIGGER trg_enforce_student_grade_rules
  BEFORE INSERT OR UPDATE ON public.student_grades
  FOR EACH ROW EXECUTE FUNCTION public.enforce_student_grade_rules();

-- บังคับให้การแก้สถานะย้อนหลังต้องมีเหตุผล (DEF-004)
ALTER TABLE public.attendance_records
  ADD CONSTRAINT attendance_edit_needs_reason
  CHECK (edited_at IS NULL OR COALESCE(btrim(edit_reason), '') <> '');
```

**ต้องระวังสองเรื่องก่อนนำไปใช้**

1. RPC `publish_final_grades` และ `unlock_course_grades` เขียน `student_grades`
   ขณะที่รายวิชาถูกล็อกหรือกำลังจะถูกล็อก ต้องตรวจว่า trigger ไม่ไปขวางการทำงานปกติ
   วิธีที่ใช้กันคือตั้งตัวแปรประจำ session ไว้ข้ามการตรวจภายใน RPC ที่เชื่อถือได้
   เช่น `SET LOCAL app.bypass_grade_lock = 'on'` แล้วให้ trigger อ่านค่านี้
2. CHECK ของ `attendance_records` จะมีผลกับแถวที่มีอยู่แล้วตอน `ADD CONSTRAINT`
   ถ้ามีแถวเก่าที่ `edited_at` ไม่ว่างแต่ `edit_reason` ว่าง migration จะล้มเหลว
   ต้องตรวจก่อนด้วย `SELECT count(*) FROM public.attendance_records
   WHERE edited_at IS NOT NULL AND COALESCE(btrim(edit_reason),'') = '';`
   แล้วเติมค่าให้แถวเหล่านั้นก่อน หรือใช้ `NOT VALID` แล้วค่อย `VALIDATE` ทีหลัง

**ลำดับที่แนะนำ** DEF-001 (วิกฤต) → DEF-005 (ผลต่อนักศึกษาโดยตรง) →
DEF-002/003/004 (ชุดเดียวกัน) → DEF-007 → DEF-006 (ต้องยืนยันนโยบายก่อน) → DEF-008
