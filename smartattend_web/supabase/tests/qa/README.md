# ชุดทดสอบ QA แบบครบวงจร

ต่างจาก `supabase/tests/` (ชุดเดิม) ตรงที่ชุดนั้นทดสอบ RPC ทีละตัวบน **สคีมาจำลอง**
ส่วนชุดนี้ apply **migration ทุกไฟล์ตามลำดับจริง** แล้วทดสอบทั้งระบบด้วยกัน
ทั้งสองชุดยังใช้งานอยู่และไม่ทับกัน

## วิธีรัน

```bash
./supabase/tests/qa/run-qa.sh                 # สร้างฐานข้อมูลใหม่ รันทั้งหมด แล้วลบทิ้ง
./supabase/tests/qa/run-qa.sh --keep          # เก็บข้อมูลทดสอบไว้ดูต่อ
./supabase/tests/qa/run-qa.sh --seed-only     # สร้างข้อมูลทดสอบอย่างเดียว
./supabase/tests/qa/run-qa.sh --teardown-only # ลบข้อมูลทดสอบอย่างเดียว
```

คืนค่า exit code ไม่เป็นศูนย์เมื่อมีกรณีที่ไม่ผ่าน จึงใช้ใน CI ได้

### รันกับฐานข้อมูลอื่น

```bash
DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres \
  ./supabase/tests/qa/run-qa.sh
```

โหมดนี้จะ **ไม่** apply migration (ถือว่าฐานข้อมูลมีสคีมาครบแล้ว)
แต่จะสร้างและลบข้อมูลที่ขึ้นต้นด้วย `TEST_` จริง

> ⚠️ ชี้ไปฐานข้อมูลที่ใช้งานจริงได้ แต่ต้องยอมรับว่าจะมีการเขียนและลบข้อมูล
> ที่ขึ้นต้นด้วย `TEST_` และบางกรณีทดสอบจะ **ประกาศผลและปลดล็อกคะแนน**
> ของรายวิชาทดสอบ ควรทำกับโปรเจกต์สำหรับทดสอบก่อน

## สามเรื่องที่ต้องเข้าใจก่อนแก้ไขชุดทดสอบนี้

### 1. ต้อง `SET ROLE` ไม่งั้นเทสต์ RLS ผ่านอย่างผิด ๆ

`postgres` เป็น superuser ซึ่ง **ข้าม RLS ทุกนโยบาย** กรณีทดสอบด้านสิทธิ์จึงต้อง
`SET ROLE authenticated` (หรือ `anon`) และตั้งตัวตนด้วย `q.act_as(uuid)` ก่อนเสมอ
ถ้าลืม เทสต์จะผ่านหมดโดยไม่ได้ทดสอบอะไรเลย

ด้วยเหตุเดียวกัน **มีเพียง `q.record` ที่เป็น `SECURITY DEFINER`**
ตัวช่วยอื่นอย่าง `q.runs` และ `q.raises` ต้องเป็น `INVOKER`
ไม่งั้น `EXECUTE` ข้างในจะรันในฐานะ `postgres` แล้วข้าม RLS

### 2. สิทธิ์ระดับตารางถูกตรวจก่อน RLS

บน Supabase จริง role `anon`/`authenticated`/`service_role` ได้สิทธิ์ตารางใน
สคีมา `public` มาตั้งแต่ต้นผ่าน default privileges ของแพลตฟอร์ม
migration ของโปรเจกต์นี้จึงเขียน `GRANT` เองเฉพาะบางตารางและพึ่งค่าปริยายกับที่เหลือ
`00_shim.sql` จำลองพฤติกรรมนี้ไว้ ถ้าไม่จำลอง เทสต์จะพังด้วย
`permission denied for table` ตั้งแต่ก่อน RLS ได้ทำงาน แล้วเราจะรายงานข้อบกพร่องผิด

**ข้อสมมตินี้ต้องยืนยันกับฐานข้อมูลจริง** ด้วยข้อ M-00 ใน
`docs/รายการตรวจสอบด้วยมือ.md`

### 3. ฐานข้อมูลต้องเป็น UTF8

ถ้าสร้างเป็น `SQL_ASCII` ฟังก์ชันอย่าง `left()` และ `length()` จะนับเป็น **ไบต์**
ไม่ใช่ตัวอักษร ทำให้ตัดคำภาษาไทยกลางตัวจนผลลัพธ์อ่านไม่ออก
`run-qa.sh` จึงสร้างฐานข้อมูลด้วย `ENCODING 'UTF8' TEMPLATE template0`

## ส่วนชดเชยที่ต้องลบออกเมื่อแก้ DEF-007 แล้ว

`run-qa.sh` มีการ `DROP VIEW` และ `DROP FUNCTION` ก่อน apply migration สามไฟล์
เพราะชุด migration ปัจจุบันรันใหม่จากฐานข้อมูลว่างไม่ผ่าน (ดู DEF-007 ใน
`docs/ข้อบกพร่องที่พบ.md`) **เมื่อแก้ข้อนั้นแล้วให้ลบส่วนชดเชยออก**
ไม่งั้นจะปิดบังปัญหาเดิมถ้ากลับมาอีก

## การเพิ่มกรณีทดสอบใหม่

ตั้งชื่อไฟล์ตามรูปแบบ `<ตัวเลขสองหลัก>_group_<ตัวอักษร>.sql` แล้ววางใน `sql/`
ตัวรันจะหยิบไปเองตามลำดับเลข และ **สร้างข้อมูลทดสอบใหม่ก่อนทุกกลุ่ม**
แต่ละกลุ่มจึงเป็นอิสระต่อกัน ไม่ต้องกังวลว่ากลุ่มก่อนหน้าจะแก้ข้อมูลทิ้งไว้

รูปแบบการเขียนหนึ่งกรณี

```sql
SELECT q.eq('F','F-01a','ชื่อกรณีทดสอบ','ผลที่คาดหวังแบบอ่านรู้เรื่อง',
            <ค่าที่ได้>, <ค่าที่ต้องการ>);
```

`q.ok` สำหรับเงื่อนไขจริง/เท็จ · `q.runs` สำหรับคำสั่งที่ต้องสำเร็จ ·
`q.raises` สำหรับคำสั่งที่ต้องถูกปฏิเสธพร้อมตรวจข้อความ
